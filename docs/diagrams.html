02 · EngineImpl

The transaction pipeline

 apply(batch)
     |
     |  fingerprint the batch content        (outside the lock)
     v
 .=========== fair mutex — one batch decides at a time ===========.
 |                                                                |
 |   load_id seen before? ---- yes, SAME content ----> return     |
 |        |                    original receipt (safe retry)      |
 |        |                                                       |
 |        +------------------- yes, DIFFERENT ------> REFUSE      |
 |        |                    loudly, apply NOTHING              |
 |        no                                                      |
 |        v                                                       |
 |   txn = nextTxn        strictly monotonic,                     |
 |        |               recovered as max(WAL, watermark)+1      |
 |        v                                                       |
 |   Scd2Applier decides every row, every table                   |
 |        v                                                       |
 |   ONE WAL record  =  all tables' changes + audit manifest      |
 |        v                                                       |
 |   write hot store,  nextTxn++                                  |
 '======================== unlock ================================'
     |
     v
 wait for fsync OUTSIDE the mutex
 ---> concurrent users share ONE group commit
     |
     v
 receipt: manifest with exact counts
Safety rail: the duplicate check runs inside the lock — racing threads get exactly one winner, always.

03 · Scd2Applier

The five-way decision, per row

 row arrives
     |
     v
 resolve entity by business key     ( ONE bulk lookup
     |                                for the whole batch )
     v
 key exists? ---- no ------------------------------> INSERT
     |                                               new entity, open interval
    yes
     v
 read NEWEST record only  (1 seek — history untouched)
     |
     v
 _op = delete? -- yes -----------------------------> TOMBSTONE
     |                                               close interval, keep history
     no
     v
 attrHash equal? -- yes ---------------------------> NO-OP
     |                                               write nothing, resends free
     no
     v
 effective time vs current start?
     |
     +-- newer or equal ---------------------------> UPDATE
     |                                               close old at eff,
     |                                               open new at eff
     |
     +-- older (back-dated) -----------------------> LATE ARRIVAL
                                                     split / reject / quarantine
Why it's fast: cost follows the 100k-row batch, never the 30M-row table.

04 · Codecs

One version record on disk

 KEY  (sorts newest-first)
 +------+---------+---------+------------+----------------+--------------+
 | 0x01 | tableId | keyHash | business   | desc(validFrom)| desc(txTime) |
 | DATA |         |         | key bytes  |      **        |      **      |
 +------+---------+---------+------------+----------------+--------------+
   ** desc(x) flips the sort: NEWEST version is the FIRST record
      under each key --> current read = one seek, any history depth

 VALUE
 +----+---------+--------+-------+-----------+----------+-----------+
 | op | validTo | txTime | txnId | schemaVer | attrHash | payload   |
 |    |         |        |       |           |   **     | (columns) |
 +----+---------+--------+-------+-----------+----------+-----------+
   ** 8-byte hash of tracked columns = the no-op detector:
      one integer compare decides "changed or not"

 KEYSPACES   0x01 DATA      0x02 KEYMAP    0x03 META    0x04 MANIFEST
             0x05 LOADID    0x06 QUARANTINE   0x07 HASHREG

05 · WAL

Group commit — 50 users, one disk flush

 user A --- txn 41 ---.
                      |
 user B --- txn 42 ---+---> WAL writer collects for
                      |     up to 2 ms / 512 txns
 user C --- txn 43 ---'
                            |
                            v
                      ONE fsync covers 41 + 42 + 43
                            |
                            v
                A, B, C all acknowledged together

 frame:  [ crc32c | len | ver | type | txnId | whole txn payload ]

 crash recovery:   torn tail at the end  --> truncate cleanly
                   corruption in middle  --> FAIL LOUDLY, never skip
Rule: nothing is acknowledged before its WAL bytes are durable. The WAL is the database; the hot store is a rebuildable cache.

07 · Catalog

Schema evolution without rewrites

 schema v1: id, name, amt
     |
     |  alter: add nullable column "tier"     --> allowed, bumps to v2
     |  alter: change business key or a type  --> REFUSED, forever
     v
 schema v2: id, name, amt, tier

 old row (written under v1) read today:
 +----------------------------+       +----------------------------------+
 | id=C1, name=Alice, amt=10  | --->  | id=C1, name=Alice, amt=10,       |
 | (v1 bytes, untouched)      |       | tier=null   (up-convert at READ) |
 +----------------------------+       +----------------------------------+
Rule: old records are never rewritten on schema change — conversion happens at read time from the schema history.

09 · Durability

Losing the machine is recoverable

 running engine
     |------- every few seconds ------->  object store   wal/ chunks
     |                                    (even the ACTIVE segment)
     '------- snapshot on schedule --->   snapshots/ zip + checksums

 DISASTER: entire data directory deleted
     |
     v
 chronodim restore --from <store>  [--as-of-txn N]
     |
     v
 newest snapshot + WAL replay  --->  fingerprint IDENTICAL
                                     every row, version, manifest back

 wal-prune:  a local segment is deleted ONLY after the shipper
             AND the publisher release it --> cleanup can never
             eat unshipped data; disk stays bounded for 10 years
