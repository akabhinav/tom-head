ChronoDim · internal architecture

The whiteboard walkthrough

How one adjustment file travels through the engine — every box, every arrow, explained the way you'd draw it for a new teammate. No prior knowledge assumed.

0. The one idea everything follows from

ChronoDim is a notebook that never uses an eraser. When a value changes, the old line is not rubbed out — it gets an end date, and a new line is written below it. When something is deleted, we write "ended here" instead of tearing out the page. That is the whole trick behind SCD Type 2, and every component below exists to do that fast, safely, and in a way Databricks can read.

Junior tip: whenever a diagram confuses you, come back to this → nothing is ever overwritten or erased. Ever. Everything else is bookkeeping.

1. The big picture — one process, three jobs

There is no server and no external database. The whole engine is one Java process around one data folder. Files go in on the left; three things come out on the right.

2. The write path — follow one file through

Say finance drops adj.json — an envelope with metadata and two records. Here is exactly what happens, in order, before the command returns "done":

  1. Read & understand the file. JSON, CSV, or JSONL is parsed. If it's an envelope, the engine pulls out load_id, effective_at, and the metadata. If it has seen this load_id before, it stops right here and returns the original receipt — that's why re-sending a file can never double-apply.
  2. Check every row. Values are converted to the declared column types, and quality gates run (not_null, ranges…). Bad rows are rejected or quarantined — your choice per table.
  3. Look up each customer's story so far. For every business key in the batch, the SCD2 brain fetches the entity's existing version chain from the hot store.
  4. Decide, per row. New key → insert. Values changed → close the old version, add a new one. Values identical → no-op, write nothing. Effective date in the past → splice it into history. (Chapter 3 draws this decision.)
  5. Journal it. Every change from this batch — plus the audit receipt — is written as one record in the WAL and physically forced to disk (fsync). This is the moment the batch becomes crash-proof.
  6. Update the hot store. The same changes are applied to RocksDB so queries see them instantly. All-or-nothing: a reader can never see half a batch.
  7. Return the receipt. The audit manifest — counts, metadata, journal position — goes back to the caller and is kept forever.

order matters: journal first, hot store second. Never the other way around.

Why journal first? If we updated the hot store first and crashed before journaling, the change would exist nowhere durable. Journal-first means the worst crash can only lose work we never said "done" for.

3. The SCD2 brain — one decision per row

Nobody sends us "insert" or "update" commands. Every row is just "here is the truth about customer C1". The brain compares it with what's already stored and picks one of five moves:

five outcomes, one rule: whatever the outcome, existing lines in the notebook are never erased

"Tracked values changed?" is answered with a hash: the engine fingerprints the columns you listed in tracked_columns. Columns in ignored_columns (like feed timestamps) can change all day without creating versions — that's what keeps re-sent snapshots free.

4. How a customer's story is stored

Inside the hot store everything is sorted key→value pairs. Two lookups matter. First the keymap turns a business key into a compact internal address. Then that address is the prefix of the customer's whole version chain, newest first:

keys are built so "newest first" is the natural sort order — the top record is always the current one

5. Reading time back — three questions, one scan

Because the chain is sorted newest-first, all three query types are the same cheap walk down one customer's records:

  • get ("what is true now?") — take the top record. If it's open and not a tombstone, that's the answer. ~21µs measured.
  • asof ("what was true on Feb 15?") — walk down to the first record whose start date ≤ Feb 15; check Feb 15 is before its end date.
  • asof --tx-time ("what did we believe on Feb 15, back in March?") — same walk, but skip any record the engine learned after March. This is the regulator question, and it works because superseded records are never erased (chapter 4's dashed row).
Two different clocks! "valid time" = when it was true in the business. "transaction time" = when the engine found out. A late correction changes the first without rewriting the second — that's bitemporal.

6. When the machine dies — why nothing is lost

The hot store keeps recent writes in memory and flushes to disk occasionally. So what happens if the process is killed between a "done" and a flush? The journal saves us:

the journal is the truth; the hot store is a fast cache of it that's allowed to lag

7. The cold tier — what Databricks sees

Seconds after every commit, the Publisher (background, dashed orange) appends the new version records to plain files in your team's column template — no engine required to read them:

the engine is the only writer here; Databricks, Spark and DuckDB are readers with zero migration
