01 · engine-api

The contract

Zero-dependency module every consumer compiles against. If it isn't here, it isn't promised.

  • Engine — the whole surface: apply, backfill, getCurrent/getAsOf/getHistory, scanCurrent/scanAsOf, manifests, quarantine, verify, snapshot.
  • TableConfig — business key (single or composite), schema history, tracked/ignored columns, valid-time mode, late-arrival/delete/error policies, publish style.
  • DataType — all 16 Spark-storable kinds, recursive array/map/struct, with coerce (input → canonical) and render (canonical → output).
  • RunId — mints time-ordered BIGINT run ids (43-bit ms + 8 node + 12 sequence bits).
Rule: the API never leaks the storage engine — no RocksDB type appears anywhere here (a test enforces it).

02 · EngineImpl

The transaction pipeline

Turns a batch of rows into exactly one atomic, durable, idempotent transaction — across all tables in the batch.

 apply(batch)
   │  fingerprint batch content        (outside the lock — cheap hash)
   ▼
 ┌─ fair mutex ─────────────────────────────────────────────┐
 │ 1. load_id seen before?                                  │
 │      same content → return original receipt              │
 │      different    → REFUSE loudly, apply nothing         │
 │ 2. txn = nextTxn        (strictly monotonic, recovered   │
 │                          as max(WAL, watermark)+1)       │
 │ 3. per table: Scd2Applier decides every row              │
 │ 4. ONE WAL record = all tables' mutations + manifest     │
 │ 5. write hot store, nextTxn++                            │
 └──────────────────────────────────────────────────────────┘
   │
   ▼  wait for fsync OUTSIDE the mutex → concurrent callers
      share one group commit instead of queueing on disk
Rule: read-decide-write is serialized; fsync-wait is shared. That is why 50 users are safe and fast.

03 · Scd2Applier

The decision engine

For each row: which entity is this, and is it an insert, update, no-op, delete, or late split? Cost follows the batch, never the table.

 100k rows in
   │ 1. group by business key
   │ 2. ONE bulk multiGet → all 100k entities resolved at once
   │ 3. per entity, read ONLY the newest record (1 seek)
   │ 4. decide:
   │      key unknown            → INSERT
   │      attrHash equal         → NO-OP  (writes nothing)
   │      differs, eff ≥ current → UPDATE (close + new open)
   │      _op delete             → TOMBSTONE close
   │      eff < current start    → LATE → split/reject/quarantine
   │ 5. > 2048 entities? shard by key-hash across all cores
   ▼
 mutations out (append-only, never an overwrite)
Rule: the full history chain is only read for late arrivals — normal adjustments touch one record per key.

04 · Codecs

Bytes on disk

Frozen record formats. Every version of an entity is one KV pair whose key sorts newest-first.

 DATA key   [0x01][tableId][keyHash][bkBytes][desc(validFrom)][desc(txTime)]
                                     └─ desc(x) = ~(x ^ MIN_VALUE):
                                        newest sorts FIRST → current
                                        read = seek + 1 record
 DATA value [ver][op][validTo][txTime][txnId][schemaVer][attrHash][bk][payload]
                                                          └─ 8-byte xxHash64 of
                                                             tracked columns =
                                                             the no-op detector
 keyspaces  0x01 DATA · 0x02 KEYMAP · 0x03 META · 0x04 MANIFEST
            0x05 LOADID · 0x06 QUARANTINE · 0x07 HASHREG
Rule: formats carry a magic + version byte and are append-only evolvable — a file written today reads forever.

05 · WAL

The write-ahead log

The database is the WAL; the hot store is a rebuildable cache of it.

 frame   [crc32c][len][ver][type][txnId][payload = whole txn]
 commit  many callers → one 2ms window → ONE fsync (group commit)
 recover replay frames; torn tail → truncate cleanly;
         interior corruption → FAIL LOUDLY (never skip silently)
Rule: nothing is acknowledged before its WAL record is durable. RocksDB's own WAL is disabled — this one is the truth.

engine-core/…/wal/WalWriter.java, WalReader.java

06 · StorageEngine

Swappable hot store

A tiny KV interface (get, multiGet, write, scan, seekIterator, snapshot) with two implementations held to the same contract test.

  • RocksDB (default) — native speed; stores a durable-txn watermark so recovery knows exactly where WAL replay must resume.
  • LSM (pure Java) — memtable → sorted segments → bloom filters → compaction. Zero native dependencies; the escape hatch when a machine can't load native libs.
Rule: both backends pass the same contract test and every differential test — switching backends can never change an answer.

engine-storage/…/RocksDbStorageEngine.java · lsm/LsmStorageEngine.java

07 · TableCatalog

Schemas that remember

Holds every table's config — including its full schema history, so rows written under schema v1 up-convert on read after v2 adds columns.

  • Compatible alters only: add nullable columns, change gates/policies/publish.
  • Refused forever: business-key changes, column type changes.
Rule: old records are never rewritten on schema change — conversion happens at read time from schema history.

08 · Publisher & Finalizer

The cold tier (→ Databricks)

Tails the WAL and appends finished SCD2 rows as open files — the Databricks side only ever appends, never MERGEs.

 WAL ──► render rows (CHRONODIM or DATABRICKS __START_AT/__END_AT style)
     ──► write part-<txnFrom>-<txnTo>.jsonl   (tmp + ATOMIC move,
          Hive partition dirs if configured)    immutable, unique name)
     ──► _chronodim_log entry = exactly-once bookmark
 Finalizer: consolidates small parts + emits current-state files.
Rule: a transaction range is rendered once; crash + republish produces byte-identical files. Readers can never see a half-written file.

09 · Durability

Backups that survive the machine

 running engine ──ship every few seconds──► object store   wal/…chunk files
                ──snapshot on demand─────►                 snapshots/…zip + checksums
 disaster:  chronodim restore --from <store> [--as-of-txn N]
            = newest snapshot + WAL replay → identical fingerprint
  • WAL pruning is veto-based: shipper and publisher must both release a segment before local deletion — cleanup can never eat unshipped data.
  • verify computes an order-independent fingerprint of the entire state — the equality check behind every recovery claim.
Rule: the active WAL segment ships in chunks — data committed seconds before a disaster is already off the machine.

10 · CLI & UI

The two front doors

  • CLI (chronodim) — every operation: table create/alter, streamed bulk load, apply (JSON/JSONL/CSV/stdin/envelope), reads, snapshot/restore/verify, run-id, bench.
  • UiServer — JDK HttpServer + one hand-written HTML page in the jar; no frameworks. The UI process is the recommended shared deployment: it holds the single-writer lock and any number of users work through it.
Rule: both doors call the same Engine API — there is no privileged path that skips validation, audit, or idempotency.

11 · Testkit

How we know it's correct

  • ReferenceScd2 — a deliberately naive second implementation (TreeMaps, no optimizations). Every differential test demands the fast engine equals the simple one, byte for byte, on both temporal axes.
  • Soaks — 300 random scenarios × both backends; 50-writer concurrency; crash/disaster drills; append-only invariant; 94 tests on every commit.
  • Scale drill (scripts/scale-drill/) — 58M rows, 5M adjustments, every current row diffed against an independent model.
Rule: every clever optimization must reproduce the answer of code with no cleverness in it.
